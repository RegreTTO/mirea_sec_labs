# ТЗ. Лаба 1: безопасный файловый менеджер

Источник: [SDLC Lab 1](https://sdlc.yonote.ru/share/SDLC_Lab_1).
Полная методичка с теорией, примерами и иллюстрациями: [локальный исходник](sources/lab-1.md).

## 1. Цель и границы

Разработать приложение для работы с файлами, JSON, XML и ZIP. Хранить пользователей, метаданные файлов и журнал действий в реляционной базе данных.

Выбранный пользователем стек:

- Python — язык приложения.
- SQLite через `sqlite3` — встроенная база данных без отдельного сервиса.
- GitHub — репозиторий [RegreTTO/mirea_sec_labs](https://github.com/RegreTTO/mirea_sec_labs).
- GitHub Actions — CI/CD; локальное выполнение описано в [лабе 2](lab-2.md).

Методичка разрешает консольный или клиент-серверный интерфейс. Для совместного выполнения обеих лаб проекту нужен сетевой режим: лаба 2 требует запуска контейнера с пробросом порта. Конкретный HTTP-фреймворк и наличие консольного клиента этим ТЗ не задаются. Отдельный веб-интерфейс не требуется.

## 2. Функциональные требования исходника

### 2.1. Диски и файловая система

- Показывать доступные локальные диски или точки монтирования.
- Показывать общий объём, свободное и доступное пользователю место.
- Показывать доступные сведения о файловой системе. Если ОС не предоставляет поле, явно сообщать об этом.
- Обрабатывать недоступные накопители без аварийного завершения приложения.

### 2.2. Файлы

- Создавать, читать, записывать и удалять файлы.
- Хранить имя, размер, дату создания, расположение и владельца файла в БД.
- Отражать создание, изменение и удаление в журнале операций.

### 2.3. JSON и XML

- Сохранять данные в JSON и XML, затем читать их обратно.
- Проверять корректность входных документов и сообщать об ошибках формата.
- Обрабатывать внешние данные как недоверенные.

### 2.4. ZIP

- Создавать ZIP-архивы и извлекать файлы из ZIP-архивов.
- Ограничивать объём распакованных данных.
- Применять контроль доступа и аудит к операциям с архивами и извлечёнными файлами.

### 2.5. Пользователи и аудит

- Реализовать аутентификацию пользователей и контроль доступа к файлам.
- Хранить хеши паролей, а не открытые пароли.
- Фиксировать действия пользователей в журнале активности в БД.
- Для значимых файловых операций сохранять время, тип действия, пользователя и связь с файлом.

## 3. Модель данных и адаптация к SQLite

Методичка предлагает таблицы `Users`, `Files` и `Operations`. Названия можно сохранить; связи и назначение должны остаться.

| Таблица | Обязательные сведения |
| --- | --- |
| `Users` | Первичный ключ, уникальный логин, хеш пароля |
| `Files` | Первичный ключ, имя, дата создания, размер, расположение, внешний ключ владельца |
| `Operations` | Первичный ключ, время, тип операции, внешний ключ файла, внешний ключ пользователя |

Уточнения для выбранной БД:

- Использовать SQLite-совместимые типы и ограничения. Не переносить `SERIAL` и `ENUM` из примера SQL буквально.
- Для SQL-запросов использовать параметры `sqlite3`, а не конкатенацию пользовательского ввода.
- Включать проверку внешних ключей для каждого соединения SQLite.
- Изменять связанные записи метаданных и аудита в транзакциях.
- Сохранять историю после удаления физического файла. Способ хранения удалённой записи выбрать при реализации; каскадное удаление аудита недопустимо.
- Учитывать, что файловая система и SQLite не образуют общую транзакцию. Ошибка записи файла или БД не должна оставлять незамеченное расхождение.
- Хранимые процедуры из рекомендаций методички не требуются: использовать параметризованные запросы и транзакции SQLite.

## 4. Уточнения безопасности для реализации

Исходник обозначает SQL-инъекции, гонки, небезопасную десериализацию и ограничения распаковки. Следующие пункты конкретизируют эти риски для проекта:

- Ограничить файловые операции рабочим каталогом приложения и правами текущего пользователя.
- Не разрешать выход из рабочего каталога через абсолютные пути, `..` и символические ссылки.
- Проверять права владельца на каждом обращении к файлу, а не только при входе пользователя.
- Использовать соль и алгоритм хеширования, предназначенный для паролей. Не записывать пароли в журнал.
- Не десериализовать недоверенные объекты через `pickle` или аналогичные механизмы выполнения кода.
- Запретить DTD и внешние сущности при чтении XML; не загружать внешние ресурсы из документа.
- При распаковке ZIP проверять пути каждого элемента, не допускать Zip Slip и выхода через ссылки.
- Ограничивать фактически записанные при распаковке байты, а не доверять только размеру в заголовке архива.
- Задать и документировать лимиты размера входных файлов, распаковки и числа элементов архива. Численные значения исходник не определяет.
- Предотвращать опасные гонки между проверкой пути и файловой операцией, а также потерю данных при одновременной записи.
- Различать успешные и отклонённые операции в аудите. Не фиксировать незавершённое изменение как успешное.

## 5. Разделение ответственности

Методичка рекомендует следующие модули; конкретные имена файлов и классов не задаются:

- Файловые операции и безопасное разрешение путей.
- Чтение и запись JSON/XML.
- Создание и безопасное извлечение ZIP.
- Работа с SQLite.
- Аутентификация и проверка доступа.
- Аудит действий пользователей.

Переиспользовать проверки путей, прав и лимитов между операциями. Не дублировать их отдельно для каждого формата.

## 6. Критерии приёмки

- Приложение запускается на Python; SQLite создаётся без установки сервера БД.
- Пользователь проходит аутентификацию и может работать со своими файлами. Доступ к чужим файлам отклоняется.
- Доступны сведения о дисках и операции создания, чтения, изменения и удаления файлов.
- JSON и XML проходят цикл записи и чтения; некорректные документы дают понятную ошибку.
- ZIP создаётся и распаковывается; выход за рабочий каталог и превышение лимитов отклоняются.
- Метаданные соответствуют выполненным операциям, а аудит остаётся доступен после удаления файла.
- Пароли не хранятся открыто; пользовательский ввод не меняет структуру SQL-запроса.
- Ошибки файловой системы, БД и параллельные обращения не приводят к незамеченной потере данных.
- Документация описывает запуск, рабочий каталог, расположение SQLite, ограничения и сценарии демонстрации.
