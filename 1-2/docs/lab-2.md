# ТЗ. Лаба 2: локальный CI/CD на GitHub Actions

Источник: [SDLC Lab 2](https://sdlc.yonote.ru/share/SDLC_Lab_2).
Полная методичка: [локальный исходник](sources/lab-2.md).
Приложение для конвейера: [файловый менеджер из лабы 1](lab-1.md).

## 1. Цель и выбранная платформа

Настроить локальный конвейер сборки, тестирования, статического анализа безопасности и запуска файлового менеджера.

- Репозиторий: [RegreTTO/mirea_sec_labs](https://github.com/RegreTTO/mirea_sec_labs).
- Приложение: Python и встроенная SQLite через `sqlite3`.
- Конфигурация CI/CD: GitHub Actions, файл `.github/workflows/main.yml` относительно корня Git-репозитория.
- Локальное выполнение того же workflow: `act` и Docker.
- GitLab, GitLab Runner и `.gitlab-ci.yml` в проект не добавлять.

Локальный контур обязателен: успешный запуск только на облачном GitHub runner не заменяет выполнение через `act`.

## 2. Общие требования исходника

- Выполнять этапы конвейера в изолированных Docker-контейнерах.
- Воспроизводить окружение без зависимости от установленных на хосте Python-пакетов.
- Прерывать конвейер при ошибке сборки, тестов или блокирующей находке SAST.
- Передавать секреты через окружение локального раннера; не хранить токены и пароли в репозитории или образе.
- Кэшировать зависимости Python для повторных запусков.
- Сохранять результат сборки или Docker-образ как артефакт конвейера.
- Использовать артефакты для передачи результатов между этапами, а не заменять артефакты кэшем.

## 3. Этапы конвейера

### 3.1. Подготовка локальной среды

- Установить Docker и `act`.
- Документировать версии и команду запуска workflow из корня репозитория.
- Подготовить локальную передачу секретов без добавления файлов секретов в Git.
- Обеспечить работу кэша и обмена артефактами при локальном запуске `act`.
- Учесть доступ контейнеров раннера к Docker для сборки и запуска приложения. Документировать выбранный способ и его риски.

### 3.2. Build

- Подготовить Python-окружение внутри контейнера и установить зависимости проекта.
- Проверить компилируемость Python-модулей и сформировать поставляемый пакет или архив приложения.
- Сохранить результат сборки как артефакт для последующих этапов.
- Не требовать отдельного нативного исполняемого файла: исходник допускает Python, а артефактом поставки может быть Docker-образ.

### 3.3. Test

- Запустить модульные тесты файлового менеджера внутри контейнера.
- Создать отчёт JUnit XML или Cobertura и сохранить его как артефакт.
- При падении тестов завершить задание с ненулевым кодом и запретить развёртывание.
- Сохранять диагностический отчёт и при падении тестов, если отчёт успел сформироваться.

### 3.4. SAST

- Запустить статический анализ исходного кода файлового менеджера.
- Сохранять отчёт анализа как артефакт.
- При находках High или Critical завершать задание с ошибкой и запрещать развёртывание.
- Зафиксировать инструмент, набор правил и соответствие уровней находок порогу блокировки.
- Semgrep приведён в методичке как пример. Если сканер использует другую шкалу, явно задать соответствие; не считать разные шкалы одинаковыми.
- Не ограничиваться сохранением отчёта: качество конвейера определяется также ненулевым кодом завершения при блокирующих находках.

### 3.5. Local Deploy

- После успешных Build, Test и SAST собрать Docker-образ приложения.
- Сохранить образ как артефакт, пригодный для локального восстановления; наличие образа только в кэше Docker недостаточно.
- Запустить контейнер локально с пробросом сетевого порта приложения.
- По умолчанию привязывать опубликованный порт к `127.0.0.1`, чтобы учебный сервис не был доступен из внешней сети.
- Проверить доступность запущенного приложения и выполнение файловой операции с записью в SQLite.
- Сохранять SQLite и рабочие файлы вне удаляемого слоя контейнера через выделенный том или каталог данных.
- Документировать остановку контейнера и удаление учебных ресурсов без случайного удаления пользовательских данных.

## 4. Адаптация GitLab CI к GitHub Actions

| Понятие исходника | Требование выбранной реализации |
| --- | --- |
| `.gitlab-ci.yml` | `.github/workflows/main.yml` |
| `stages` | Отдельные `jobs` и явные зависимости `needs`; ключ `stages` не переносить |
| GitLab Runner | Локальное выполнение GitHub Actions через `act` |
| `image` у задания | Контейнерное окружение задания или явный запуск инструмента в Docker |
| `artifacts` | Сохранение и получение артефактов средствами GitHub Actions с поддержкой локального запуска |
| `cache` | Кэш зависимостей pip, совместимый с GitHub Actions и выбранным запуском `act` |
| `dotnet restore/build/test` | Установка Python-зависимостей, сборка Python-поставки и запуск Python-тестов |
| JUnit или Cobertura | Реальный XML выбранного формата, а не переименованный отчёт другого типа |

Build выполняется перед Test и SAST. Test и SAST могут выполняться параллельно. Local Deploy зависит от успешного завершения обоих заданий.

События запуска workflow исходник не задаёт. При реализации нужно документировать автоматический запуск проверки изменений и явный локальный запуск развёртывания. Облачный runner не должен считаться развёртыванием на компьютере студента.

## 5. Dockerfile и данные

- Использовать многоступенчатую сборку.
- Не переносить инструменты сборки и тестирования в финальный runtime-образ без необходимости.
- Запускать приложение от непривилегированного пользователя.
- Предоставлять этому пользователю права только на рабочие файлы и SQLite, необходимые приложению.
- Хранить зависимости и версии окружения так, чтобы повторный запуск использовал тот же набор инструментов.
- Не включать в образ секреты, локальную БД, пользовательские данные и отчёты предыдущих запусков.
- Отдельный контейнер PostgreSQL или MySQL не нужен: SQLite работает в процессе приложения.

## 6. Безопасность локального контура

- Проброс Docker-сокета даёт заданиям управление Docker-хостом. Использовать его только для доверенного учебного workflow.
- Не запускать недоверенные pull request на локальном раннере с Docker-сокетом или привилегиями.
- Не включать `privileged` и Docker-in-Docker без обоснованной потребности.
- Не передавать секреты в отчёты, артефакты, логи и слои образов.
- Выдавать workflow только необходимые разрешения GitHub.
- Не публиковать образ в registry и не менять удалённую инфраструктуру: исходное задание требует локального запуска.

## 7. Результаты и критерии приёмки

- В репозитории есть workflow GitHub Actions и многоступенчатый Dockerfile.
- Одна и та же конфигурация конвейера запускается локально через `act`.
- Build, Test, SAST и Local Deploy выполняются в контейнерном окружении с явными зависимостями.
- Получены артефакт сборки, XML-отчёт тестов, отчёт SAST и сохранённый Docker-образ.
- Повторный запуск использует кэш зависимостей.
- Ошибка теста или блокирующая находка SAST останавливает конвейер до Local Deploy. Для демонстрации использовать временное контролируемое изменение, не оставляя уязвимость в рабочем коде.
- Контейнер работает не от root, доступен через локальный опубликованный порт и использует SQLite.
- Перезапуск контейнера сохраняет рабочие файлы, пользователей и аудит в выделенном хранилище.
- Инструкция описывает подготовку, передачу секретов, запуск, получение артефактов, проверку приложения и остановку.
- Результат лично защищён преподавателю и загружен в `online-edu.mirea.ru`.

## 8. Рекомендации исходника, не обязательные для проекта

- Dev Containers предложены как способ унифицировать рабочее окружение; отдельный `devcontainer.json` не обязателен.
- Trivy и CodeQL предложены как альтернативы. Конкретный SAST-инструмент выбирается с учётом Python и локального запуска через `act`.
- GitLab-пример остаётся только в [снимке методички](sources/lab-2.md).
- В исходной второй методичке изображений нет.
