# CI и публикация образа

GitHub Actions собирает Python-пакет, проверяет его тестами и анализирует исходники через Bandit.
После успешных проверок конвейер собирает Docker-образ из проверенного wheel.
Из `main` образ публикуется в `ghcr.io/regretto/mirea-file-manager:sha-<полный SHA коммита>`.
Тег `latest` не используется. Деплоя и сетевого API нет.

## Устройство

- `.github/workflows/main.yml` в корне репозитория — Build, Test, SAST, Image и Publish с явными зависимостями.
- `1-2/ci/` — закреплённые зависимости инструментов, подготовка Python, порог SAST и локальный запуск.
- `1-2/tests/` — проверки поведения файлового менеджера и CLI на установленном wheel.
- `1-2/Dockerfile` — установка wheel и зависимостей в отдельной стадии; runtime работает с UID/GID `10001:10001`.
- `1-2/.dockerignore` — в контекст сборки попадают только Dockerfile, wheel и экспорт зависимостей.

Build передаёт wheel, sdist, зависимости с хешами и контрольные суммы через артефакт `python-package`.
Test устанавливает этот wheel без editable-режима. SAST проверяет исходники той же ревизии.
Image получает артефакт Build; Publish получает сохранённый образ Image, а не пересобирает его.
Кэш pip/uv ускоряет повторные запуски, но не заменяет артефакты.

## Локальный запуск

Нужны Git-checkout всего репозитория, Docker и `act`. На macOS:

```sh
brew install act
open -a Docker
```

Из корня репозитория:

```sh
bash 1-2/ci/run-local.sh
```

Скрипт выбирает Docker endpoint активного контекста и запускает `workflow_dispatch`.
Образ раннера закреплён digest. На Apple Silicon при необходимости явно задайте архитектуру:

```sh
bash 1-2/ci/run-local.sh --container-architecture linux/arm64
```

Хостовые Python-пакеты не используются: инструменты и приложение устанавливаются в контейнерах.
Python закреплён на `3.12.12`; CI-инструменты и их транзитивные зависимости — в `ci/requirements.txt` с хешами.
Build backend закреплён отдельно в `ci/build-constraints.txt`; зависимости приложения берутся из `uv.lock`.
Для обновления CI-инструментов измените `ci/requirements.in` и выполните из `1-2/`:

```sh
uv pip compile ci/requirements.in --python-version 3.12 --generate-hashes --universal -o ci/requirements.txt
```

По умолчанию локальные артефакты находятся в `~/.cache/mirea-security-lab2/artifacts`, кэш — в соседнем `cache/`.
Переменная `LAB2_CI_STATE` задаёт другой каталог. Повторный запуск с тем же каталогом переиспользует кэш.
Для проверки попадания в кэш найдите в выводе `Cache restored from key`.
GitHub Actions хранит пакет и отчёты 7 дней, образ — 3 дня.

`act` требует включённый сервер артефактов для upload/download-artifact v4; скрипт задаёт `--artifact-server-path`.
Серверы артефактов и кэша доступны контейнерам через интерфейс хоста. Используйте доверенную локальную сеть:
артефакты учебной работы не должны содержать секреты. Не открывайте порты этих серверов во внешнюю сеть.
[Документация act](https://nektosact.com/usage/index.html).

## Секреты и границы локального раннера

Локальная проверка не требует GitHub-токена или пароля приложения. Smoke-проверка генерирует одноразовый пароль в памяти.
Пароль не передаётся аргументом команды и не выводится в отчёты. Временные контейнеры и том удаляются после проверки.
Не используйте `set -x` и не сохраняйте `docker inspect` контейнеров, которым переданы секреты через окружение.

Если GitHub ограничивает анонимную загрузку actions, передайте отдельный минимальный токен через окружение `act`:

```sh
# GITHUB_TOKEN заранее загружен в окружение из вашего менеджера секретов.
bash 1-2/ci/run-local.sh -s GITHUB_TOKEN
```

Не записывайте значение токена в командную строку вручную, Git, `.env`, Dockerfile или отчёты.
Локальный event содержит `act: true`; задание Publish при нём пропускается. Дополнительная проверка встроенной переменной `ACT` запрещает локальную публикацию даже без event-файла.
Не запускайте Publish локально с изменённым event и токеном с правом записи пакетов.

`act` получает Docker-сокет для сборки и smoke-проверки образа. Доступ к сокету означает контроль над Docker-хостом.
Запускайте только проверенный учебный workflow. Не выполняйте недоверенные PR локально и не включайте `privileged`.
Это относится ко всему workflow: даже job тестов может содержать недоверенный код.

## SAST и блокировки

Bandit `1.8.6` выполняет полный стандартный набор Python-правил для `src/file_manager`.
`--ignore-nosec` не позволяет скрыть находку комментарием `nosec`; baseline и исключений правил нет.
JSON содержит все уровни находок. После сканирования `ci/check_sast.py` проверяет полноту отчёта и порог.
[Параметры Bandit](https://bandit.readthedocs.io/en/latest/man/bandit.html).

- Bandit `HIGH` соответствует блокирующему порогу задания High/Critical.
- Собственного уровня `Critical` у Bandit нет; gate отклоняет и `CRITICAL`, если такой уровень появится в отчёте.
- `MEDIUM` и `LOW` остаются в отчёте, но не блокируют конвейер.
- Ошибка сканирования, пустой охват, повреждённый или отсутствующий отчёт завершают SAST с ошибкой.

Ненулевой код pytest, SAST или сборки не допускает Image и Publish.
JUnit XML и JSON Bandit загружаются через `always()`, если соответствующий отчёт успел сформироваться.

Для демонстрации отрицательного результата используйте отдельный временный checkout, не основной каталог приложения:

1. Добавьте временный тест `def test_failure(): assert False` в `1-2/tests/test_failure_demo.py` и запустите workflow.
2. Убедитесь, что Test завершился с ошибкой, `test-report` сохранён, Image и Publish пропущены. Удалите временный тест.
3. Добавьте временный файл `1-2/src/file_manager/sast_demo.py` со строками `import subprocess` и `subprocess.run(input(), shell=True, check=True)`.
4. Повторите запуск: Bandit B602 имеет уровень HIGH, SAST должен завершиться с ошибкой; Image и Publish пропускаются.
5. Удалите временный файл. Не коммитьте контролируемые ошибки и уязвимости.

Никогда не запускайте демонстрационный уязвимый файл. Он нужен только для статического анализа.

## Docker-образ и GHCR

Pull request выполняет Build, Test, SAST и Image без публикации.
Push в `main` и ручной запуск workflow на `main` добавляют Publish. Ручной запуск другой ветки не публикует образ.
Только Publish получает `packages: write`; остальные задания имеют `contents: read`.
Авторизация GHCR использует встроенный `GITHUB_TOKEN`; отдельный PAT для workflow не требуется.

Проверьте настройки репозитория: GitHub Actions должны быть разрешены, а политика организации не должна запрещать запись в Packages.
Первую публикацию можно выполнить после слияния PR lab2 в `main`.
Видимость пакета регулируется настройками GHCR; workflow не делает пакет публичным.
Для приватного образа пользователю нужен доступ к пакету и собственная авторизация `docker login ghcr.io`.

Восстановление образа из артефакта `docker-image` после распаковки:

```sh
sha256sum -c image.sha256
docker load --input image.tar.gz
```

Архитектура образа соответствует Docker builder: локально Apple Silicon — arm64, GitHub ubuntu-24.04 — amd64.
Multi-platform manifest не создаётся. Для использования образа другой архитектуры требуется совместимая эмуляция.

Ручной запуск опубликованного CLI, замените `<SHA>` полным SHA опубликованного коммита:

```sh
image='ghcr.io/regretto/mirea-file-manager:sha-<SHA>'
docker run --rm "$image" --help
docker volume create --label ru.mirea.security.lab2=manual mirea-lab2-data
docker run --rm -it --mount type=volume,src=mirea-lab2-data,dst=/data "$image" register
docker run --rm -it --mount type=volume,src=mirea-lab2-data,dst=/data "$image" login
docker run --rm --mount type=volume,src=mirea-lab2-data,dst=/data "$image" file create hello.txt --text hello
docker run --rm --mount type=volume,src=mirea-lab2-data,dst=/data "$image" file read hello.txt
```

CLI завершается после команды; постоянно работающего контейнера и опубликованных портов нет.
Пользователи, сессия, рабочие файлы и SQLite находятся в томе `/data`.
Не монтируйте существующую пользовательскую `.data/` для CI или демонстрации.

Каждая команда использует `--rm`, поэтому остановка сервиса не требуется.
Удалять том следует только после проверки его имени и содержимого: это удалит учебные файлы, пользователей и аудит.
Не используйте `docker system prune --volumes`.

```sh
docker volume inspect mirea-lab2-data
# Только если данные больше не нужны:
docker volume rm mirea-lab2-data
```

## Отличия от методички

По прямому указанию пользователя Local Deploy заменён публикацией образа в GHCR.
Требования о сетевом порте и запрете registry не применяются; CLI приложения не меняется.
GitLab/.NET заменены GitHub Actions/Python. Исходная методичка сохранена без изменений в `sources/lab-2.md`.
