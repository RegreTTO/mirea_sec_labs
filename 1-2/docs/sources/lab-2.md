## Задание по настройке локального конвейера непрерывной интеграции и доставки (CI/CD)

Цель задания — развернуть локальный CI/CD контур на компьютере студента для автоматизации процессов сборки, тестирования и анализа безопасности кода. Студент должен научиться эмулировать работу серверов CI/CD в локальной среде, понимать принципы работы изолированных раннеров и интегрировать инструменты DevSecOps.

1. **Изоляция и воспроизводимость**: Все шаги конвейера должны выполняться в изолированных Docker-контейнерах, чтобы исключить влияние локальной операционной системы на результаты сборки.
2. **Статический анализ кода (SAST)**: В конвейер должен быть интегрирован инструмент поиска уязвимостей (например, Semgrep), который будет автоматически прерывать сборку при обнаружении критических ошибок.
3. **Безопасное управление секретами**: Токены и пароли не должны храниться в коде. Они должны передаваться через переменные окружения локального раннера.
4. **Кэширование зависимостей**: Настройка кэширования пакетов (nuget, npm, pip) для ускорения повторных запусков конвейера.
5. **Генерация артефактов**: Скомпилированный бинарный файл или Docker-образ должны сохраняться как артефакты конвейера для последующего использования.

---

### Функциональные требования к конвейеру

Программа и инфраструктура должны включать следующие этапы:

1. **Подготовка локального раннера**:

   - Установка Docker и развертывание локального исполнителя. Для GitLab CI используется официальный образ `gitlab/gitlab-runner` с привязкой к Docker-сокету. Для GitHub Actions используется утилита `act`.
2. **Стадия сборки (Build)**:

   - Компиляция исходного кода тестового приложения (C#, Python или Node.js) внутри контейнера.
3. **Стадия тестирования (Test)**:

   - Запуск модульных тестов с генерацией отчета в формате JUnit или Cobertura.
4. **Стадия безопасности (SAST)**:

   - Запуск сканера уязвимостей. При нахождении проблем уровня High или Critical джоба должна завершаться с ошибкой.
5. **Стадия развертывания (Local Deploy)**:

   - Сборка Docker-образа приложения и его локальный запуск с пробросом портов.

---

### Требования к структуре проекта

1. **Dockerfile**:

   - Многоступенчатая сборка (multi-stage build) для минимизации размера финального образа.
   - Запуск приложения от имени непривилегированного пользователя внутри контейнера.
2. **Файл конфигурации CI/CD** (`.gitlab-ci.yml` или `.github/workflows/main.yml`):

   - Явное объявление стадий (`stages`).
   - Использование артефактов (`artifacts`) для передачи данных между стадиями.
   - Использование кэша (`cache`) для директорий с зависимостями.
3. **Тестовое приложение**:

   - Разработанный код файлового менеджера

### Пример схемы конфигурации (GitLab CI):

```yaml
stages:
  - build
  - test
  - sast
  - deploy

variables:
  DOCKER_DRIVER: overlay2

build_app:
  stage: build
  image: mcr.microsoft.com/dotnet/sdk:8.0
  script:
    - dotnet restore
    - dotnet build --configuration Release
  artifacts:
    paths:
      - bin/Release/

run_tests:
  stage: test
  image: mcr.microsoft.com/dotnet/sdk:8.0
  dependencies:
    - build_app
  script:
    - dotnet test --logger "trx;LogFileName=test-results.trx"
  artifacts:
    reports:
      junit: test-results.trx

security_scan:
  stage: sast
  image: returntocorp/semgrep
  script:
    - semgrep scan --config auto --error .

local_deploy:
  stage: deploy
  image: docker:24.0
  services:
    - docker:24.0-dind
  script:
    - docker build -t myapp:latest .
    - docker run -d --rm -p 8080:80 myapp:latest
```

## Теоретическая часть.

### Принципы CI/CD и локальные раннеры

Непрерывная интеграция (CI) и непрерывная доставка (CD) — это практики автоматизации процессов разработки. В корпоративной среде для этого используются выделенные серверы (GitLab CI, Jenkins, GitHub Actions). Однако для обучения и отладки конвейеров требуется локальная среда.

Локальный раннер — это агент, который забирает задания из очереди и исполняет их на машине разработчика.

- **GitLab Runner** может быть запущен в Docker-контейнере. Для сборки Docker-образов внутри контейнера раннера используется либо сервис `docker:dind` (Docker-in-Docker), либо проброс сокета `/var/run/docker.sock`.
- **act (nektos/act)** — утилита, которая читает файлы GitHub Actions (`.github/workflows/*.yml`) и транслирует их в локальные Docker-контейнеры, эмулируя виртуальные машины GitHub.

### Конфигурация конвейера

Конвейер состоит из стадий (stages), которые выполняются последовательно. Внутри стадий параллельно выполняются задания (jobs).

- **Архивы и Артефакты**: Артефакты позволяют передавать файлы (например, скомпилированные бинарники или отчеты о тестах) между стадиями. После завершения конвейера артефакты удаляются (по истечении TTL).
- **Кэш**: В отличие от артефактов, кэш используется для ускорения сборки путем сохранения зависимостей (например, папки `~/.nuget/packages` или `node_modules`) между запусками конвейера.

### Статический анализ безопасности (SAST)

SAST-инструменты анализируют исходный код на наличие известных паттернов уязвимостей без его выполнения. В локальном CI/CD это позволяет разработчику получить обратную связь до того, как код попадет в удаленный репозиторий. Инструменты вроде Semgrep или SonarQube легко интегрируются в конвейер как отдельные джобы. При обнаружении уязвимостей скрипт возвращает ненулевой код завершения, что автоматически прерывает выполнение конвейера.

### Безопасность локального CI/CD

При настройке локального раннера с поддержкой Docker возникает риск побега из контейнера (Container Escape).

1. **Проброс Docker-сокета**: Монтирование `/var/run/docker.sock` внутрь контейнера раннера дает ему полный контроль над хостовой машиной. Это допустимо только на локальном компьютере разработчика и недопустимо в продакшене.
2. **Docker-in-Docker (DinD)**: Запуск дочернего демона Docker внутри контейнера. Требует привилегированного режима (`privileged: true`), что также несет риски, но обеспечивает лучшую изоляцию файловых систем по сравнению с пробросом сокета.
3. **Секреты**: Локальные переменные окружения должны использоваться для хранения токенов доступа к приватным репозиториям или базам данных.

---

**Предложение лучшего решения:** Если цель курса — максимально приблизить студентов к современным реалиям без необходимости разворачивать тяжелый GitLab Runner или сталкиваться с проблемами прав доступа к Docker-сокету на Windows/Mac, лучше использовать связку **GitHub Actions + утилита** `act` + Dev Containers (VS Code).

1. `act` работает быстрее и проще настраивается локально, читая стандартные `.github/workflows`.
2. Использование `DevContainers` (файл `devcontainer.json`) гарантирует, что у всех студентов будет абсолютно идентичное окружение (инструменты CLI, версии SDK), что полностью исключает проблему "у меня на машине работает".
3. В качестве SAST-сканера лучше использовать `Trivy` или `CodeQL`, так как они имеют нативную поддержку в виде готовых экшенов и лучше встраиваются в учебный процесс по безопасности.
